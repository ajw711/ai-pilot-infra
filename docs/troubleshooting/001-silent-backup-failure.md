# [Troubleshooting] 백업 파이프라인의 Silent Failure

## 상황

PostgreSQL → Cloudflare R2 오프사이트 백업 자동화(CronJob)를 구축하고 실제 스케줄(매일 21:00 KST) 대로
운영을 시작했다. 며칠 뒤 백업 실행 로그를 점검하던 중, `dump` 컨테이너 로그에 아래와 같은 에러가 있는데도
`upload` 컨테이너는 정상 완료 메시지를 출력한 것을 발견했다.

```
[dump 컨테이너 로그]
[1/2] pg_dump 시작...
pg_dump: error: connection to server at "postgres-postgresql" (10.43.75.4), port 5432 failed: Connection refused
[2/2] 파일 크기 확인...
-rw-r--r-- 1 root root 20 Aug 9 12:49 /backup/backup-20260809-124938.sql.gz

[upload 컨테이너 로그]
R2 업로드 중: backup-20260809-124938.sql.gz
upload: ../backup/backup-20260809-124938.sql.gz to s3://ai-pilot-db-backup/postgres/...
백업 완료: backup-20260809-124938.sql.gz
```

`kubectl get jobs`에서도 해당 Job은 `Complete 1/1`로 표시되어 있었다. 겉보기엔 완전히 정상인 백업이었지만,
실제로는 **20바이트짜리 빈 파일**이 "백업"이라는 이름으로 R2에 업로드되어 있었다.

## 원인

원본 스크립트는 아래와 같은 구조였다.

```sh
set -e
PGPASSWORD="${DB_PASSWORD}" pg_dump ... | gzip > "/backup/${FILENAME}"
```

`set -e`는 스크립트 내 명령어가 0이 아닌 종료 코드를 반환하면 즉시 중단시키는 옵션이다. 하지만 셸의 기본
동작에서 **파이프라인(`|`)의 종료 코드는 마지막 명령어의 것만 반영**된다. 즉:

- `pg_dump`가 연결 실패로 종료 코드 1을 반환해도
- `gzip`은 (입력이 비어있을 뿐) 정상적으로 종료 코드 0을 반환하므로
- 셸 전체는 "성공"으로 판단하고 다음 줄로 넘어간다

그 결과 `pg_dump` 실패가 **조용히 무시**되고, 빈 덤프 파일이 정상 백업인 것처럼 업로드 단계까지 흘러갔다.

이 특정 사례에서 `pg_dump`가 연결에 실패한 근본 원인은 별도 이슈([WSL2 클러스터 불안정 문제](./wsl2-cluster-not-ready.md))였지만,
그 원인과 무관하게 **파이프라인의 실패를 감지하지 못하는 구조 자체가 더 근본적인 결함**이었다.

## 해결

1. `set -e`를 `set -euo pipefail`로 교체 — 파이프라인 중 어느 한 단계라도 실패하면 전체를 실패로 처리
2. 덤프 완료 후 파일 크기를 검증하는 방어 로직 추가 — 정상적인 덤프라면 최소 1KB는 넘는다는 전제로,
   그보다 작으면 명시적으로 `exit 1`
3. 업로드 스크립트에도 동일한 크기 검증을 이중으로 추가 — dump 단계 검증을 우회해서 업로드로 넘어가는
   경로가 생기더라도 마지막 방어선 확보

```sh
set -euo pipefail
...
SIZE=$(stat -c%s "/backup/${FILENAME}")
MIN_SIZE=1024
if [ "$SIZE" -lt "$MIN_SIZE" ]; then
  echo "ERROR: 백업 파일이 비정상적으로 작습니다 (${SIZE} bytes)."
  exit 1
fi
```

수정 후에는 동일한 상황이 발생하면 `dump` 컨테이너가 명시적으로 실패하고, Job 상태도 `0/1`로 표시되어
`kubectl get jobs`만 봐도 바로 인지할 수 있다.

## 교훈

- **파이프라인의 성공/실패는 마지막 명령어 기준**이라는 셸의 기본 동작을 잊기 쉽다. 데이터를 다루는
  스크립트(특히 백업/마이그레이션)에서는 `pipefail`을 습관적으로 켜두는 것이 안전하다.
- **"로그에 완료 메시지가 찍혔다"는 것과 "실제로 유효한 결과물이 만들어졌다"는 것은 다른 문제**다.
  자동화 파이프라인은 실행 자체의 성공 여부뿐 아니라 산출물의 최소한의 유효성(크기, 포맷 등)까지
  검증해야 신뢰할 수 있다.
- 이 버그를 방치했다면, R2에는 계속 "성공"으로 기록된 빈 백업만 쌓였을 것이고, 실제로 복구가 필요한
  순간에야 백업이 전부 무효하다는 사실을 알게 됐을 것이다. 백업 시스템에서는 이런 실패가 가장 치명적이다.

## 수정 후 검증

수정을 반영한 뒤 두 가지 시나리오로 실제 동작을 확인했다.

**정상 케이스**: 수동으로 Job을 실행해 기존과 동일하게 정상 크기(198.0K)의 백업이 만들어지고
R2 업로드까지 정상 완료되는 것을 확인했다. `pipefail` 추가가 정상 동작을 깨뜨리지 않는다는
것을 검증했다.

**실패 케이스**: 존재하지 않는 호스트(`wrong-host`)로 의도적으로 `pg_dump`를 실패시키는
테스트 Pod를 실행했다.

```
pg_dump: error: could not translate host name "wrong-host" to address: Try again
```

- Pod 상태: `Error` (기존이라면 `Completed`로 조용히 성공 처리됐을 상황)
- 로그에 `pg_dump` 이후의 명령어(`gzip`, 이후 `echo`)가 전혀 실행되지 않음

수정 전이었다면 이 상황에서도 빈 파일이 생성되고 업로드까지 조용히 "성공"으로 처리됐겠지만,
`pipefail` 적용 이후에는 `pg_dump` 실패 시점에 파이프라인 전체가 즉시 중단되고 Job이 명시적
으로 실패 상태가 되는 것을 확인했다.
